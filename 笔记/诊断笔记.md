## 2. 现象 → 根因 → 处理

| 现象/错误 | 常见根因 | 处理 |
|---|---|---|
| STM32 `must be ASCII`、字段不是 55、NUL/乱码 | 充电器导致链路断开，或串口电气状态异常 | 拔掉充电器，重启 STM32/Orin 后先跑只读诊断 |
| `serial is already owned` / `Could not exclusively lock` | RL、Collector 或 ACT 重复启动 | 用 `fuser`/`pgrep` 找具体 Owner，通过原 UI/终端正常停止 |
| `sensor_valid=false`、新状态 0 Hz | STM32 未复位、传感器链路失效或仍在充电 | 检查供电/充电器、复位 STM32，再诊断 |
| `/joint_states` 无数据 | Orin 状态流、UDP 18081 或 PC bridge 未运行 | 查 Orin Runtime、端口和 Operator profile |
| JointState 有但 RViz 某关节不动 | 映射、单位、关节名或 URDF/TF 问题 | 对照 Web UI 原始角度与 `/joint_states`，逐关节检查 |
| `local_map.timestamp_s 已过期或来自未来` | PC/Orin 时间不同步，或 LocalMap 没有新数据 | 检查 Chrony/systemd-timesyncd，再查感知栈 |
| `live planning inputs did not become fresh` | AiryLidar Operator/雷达/地图没启动或时间戳失效 | 启动 `live_commissioning`，逐级查点云→地图→状态 |
| UI 无相机，显示“等待 Collector” | 未启动 Collector 时属正常；运行中则是 18092/设备 Owner 问题 | 查 `/healthz`、相机 Owner 和 by-path 设备 |
| `docker: bad format for path ...by-path...:/dev/video0` | USB by-path 名含冒号，直接传给 Docker 解析歧义 | 当前脚本已先 `readlink -e` 为 `/dev/videoN`；确认 Orin 代码已同步 |
| import-only Docker 检查提示 `NVIDIA Driver was not detected` | 命令未传 GPU，仅做 Python import | 属正常；真推理用项目 launcher 并运行 GPU 诊断 |

| ACT 完成后 `ACT-to-RL handoff was revoked` | 已发现两条独立路径：旧版 status 混合快照；目标模式零回显未等完整安全门就提前激活，随后被同一帧撤权 | 同时更新 Orin 原子 status 与 target-mode safety claim 修复；不要放宽安全门或仅增大 timeout |

### 6.1 2026-08-24：ACT 结束时的 control status 混合快照

**现象**

- 自动多铲的第一次 ACT 挖掘完成后停止，未进入 RL 倾倒。
- UI 报 `RuntimeError: ACT-to-RL handoff was revoked`。
- 同期日志显示 `prepared follow ready`、`sensor_valid=True`，ACT worker 也未提前断开。
- 随后的 `resident motion core disarmed` 是 PC 检测到错误后的正常安全清理，不是首发原因。

**根因**

Orin 的 `resident_motion_control.v1` status 旧实现先读
motion authority，再单独读 ACT segment。ACT 最后一条命令 ACK
正好在两次读取之间到达时，一个 status 会同时包含：

- 交接前：`active=act_dig` 且 `target=null`；
- 交接后：`act_segment_complete=true` 且 `act_is_active=false`。

这个组合在任何真实时刻都不存在，但 PC 会将它按真实撤销处理。
因此故障具有偶发性：同一套代码可能成功运行三铲，也可能在某次
ACT→RL 切换时触发。

**解决方法**

- Orin `ResidentMotionCore` 新增单一原子 control status 快照。
- motion authority、ACT segment、RL/ACT active、Mission lease 和
  operational 状态全部在同一把 control lock 内读取。
- 保留 PC 对真实交接撤销的 fail-closed 判断；不增大 timeout，不放宽
  传感器或串口 ACK 门禁。
- 增加确定性并发回归：强制最后 ACK 落在两次旧读取之间，旧版
  稳定复现现场矛盾 status，修复后通过。

**后续结论**

这是真实竞态，但 13:33 使用原子 status 版本仍复现相同 UI 错误，
说明它不是全部根因。该修复应保留；不能再把它单独视为现场问题已经闭环。

### 6.2 2026-08-24：目标 RL 零回显安全未就绪时被提前激活

**现象与证据**

- ACT 130 steps 正常完成，prepared DUMP trajectory 已就绪。
- Orin 没有串口 timeout、CSV parse failure、Mission lease expiry 或 ACT
  worker 提前断连记录。
- 失败只发生在 ACT 最后一条命令 ACK 后的 ACT→RL 零命令交接窗口。
- 公共 `ResidentCommandSink` 回归可稳定复现同一个 authority 结果：
  目标 velocity-reference 零命令的序号、模式和动作都匹配，但
  `control_enabled=false` 时，旧实现先进入 active RL，随后立即安全撤权，
  generation 再次增加且 `target=null`；PC 因而报告
  `ACT-to-RL handoff was revoked`。

**根因**

旧 `_ack_matches_locked()` 把目标模式零回显只当作“命令 ACK”验证，
没有把 `control_enabled`、`estop`、`sensor_valid`、`stm32_alive`、
`fault_flags`、`command_valid/timed_out` 和目标 control mode 作为一个
完整的目标策略激活门。目标模式刚切换时若第一帧安全状态尚未收敛，
就会出现“先 active，再被同一帧 fail-closed 撤权”的瞬态。

**解决方法**

- terminal source zero 之后继续保持零命令和 `target_zero_pending`。
- 目标零回显只有在完整 safety predicate 同时成立时才 ACK 并激活 RL。
- 未就绪帧不激活任何策略、不发送非零命令，也不撤销交接代次；下一帧
  安全回显可完成同一交接。
- PC 撤权异常增加原子 status 摘要：phase、generation、active/target、
  ACT segment steps、RL/ACT active 和 Mission lease，便于后续直接定位。
- 新增回归覆盖 unsafe target zero → 保持 pending → safe target zero →
  active RL 的完整时序。

**当前状态**

已于 2026-08-24 13:45 完成真机自动 3 铲复测：3 次 ACT→RL
均进入 Follow，任务最终输出“装车循环完成：3/3”，无
`ACT-to-RL handoff was revoked`。终态零命令得到 STM32
回显确认，串口、ACT data link 与 control socket 正常释放。
本故障的现场功能闭环已完成。

**复测顺序**

1. 同步新版 `excavator-orin-runtime` 后确认串口/相机无 Owner 残留。
2. Web UI “开始分阶段验证”：RL 到挖点 → ACT 挖掘 → RL 倾倒。
3. 自动 1 铲。
4. 自动 3 铲，确认每次 ACT→RL 都进入 Follow，无
   `ACT-to-RL handoff was revoked`。

### 6.4 2026-08-24：7 铲复测中 ACT→RL 再次变慢，末次 RL 返回不收敛

**现场日志**

- Mission 基名：`hybrid_mission_20260824_143007`。
- 7 次 RL→ACT 交接延迟为 147.8–254.2 ms，均值 192.8 ms；该方向正常。
- 7 次 ACT→RL 交接延迟为 7902.1、8070.2、4728.2、6066.9、
  621.0、6315.3、4772.5 ms，均值 5496.6 ms、中位数 6066.9 ms。
- ACT→RL 的目标零命令确认和首条非零 STM32 ACK 仍分别约 49–114 ms
  和 44–52 ms；平均 `policy_ready_wait_ms=5375.4`，因此慢点不在串口、
  常驻 ACT worker 或 motion authority 原子换权。
- prepared DUMP 共 7 次尝试：6 次生成 ready trajectory，其中 5 次因首
  waypoint 与交接时新鲜铲尖距离为 0.2692–0.4088 m 而安全回退，1 次直接
  Follow 成功；另 1 次尚在规划时被取消。实际复用率仅 1/7。
- 最后一次 RL 返回 `dig_02` 是另一项独立异常：Follow 连续输出 790 个
  action datagram，始终停留在 waypoint 1/3；距离从 0.3538 m 增大并长期
  停在约 0.642 m，最终 Mission 终止后报告 `MOTION_GATE_CLOSED`。
  全程 STM32 `sensor_valid=True`，所以不能把这段约 40 秒停留解释为策略
  冷启动或 ACT→RL 换权等待。

**已确认根因：prepared 起点过早冻结**

当前 `prepared_dump_lead_steps=20`，ACT 以 10 Hz 执行，因此 DUMP 规划在
ACT 结束前约 2 秒冻结实时铲尖状态。ACT 在余下 20 steps 中仍会显著改变
铲尖位置，导致交接时预规划轨迹首点已落后于真实状态。活动配置的
`prepared_start_tolerance_m=0.15` 正确阻止了不连续轨迹直接执行；不应把
阈值放宽到 0.3–0.5 m 来换取表面流畅。

**解决方案与验收计划**

1. 保留 0.15 m 激活安全门和 STM32 ACK 级换权，不修改安全语义。
2. 将“规划进程预热”和“冻结规划起点”分离：ACT 早期只让 planner/service
   常驻；临近 ACT 终点时再用最新铲尖状态生成 trajectory。若一次规划无法
   在剩余窗口完成，应显式报告 fallback，不静默把重新规划时间算成策略换权。
3. 先用 5/10/15 个 lead steps 做发动机关闭或受控真机对比，记录每次规划
   用时、交接首点偏差、prepared 是否直接激活和 ACK 级 handoff；选择满足
   规划完成率且首点偏差稳定小于 0.15 m 的最晚触发点，而不是直接猜参数。
4. 为 RL Follow 增加低频、结构化诊断证据：目标 waypoint、实际铲尖、归一化
   策略输出、转换后的物理速度、STM32 回显动作及死区/限位裁剪原因。再次出现
   “datagram 增长但距离不收敛”时，才能区分输出方向错误、动作落入死区、
   坐标契约不一致或液压执行未响应。
5. 回归验收至少连续 7 铲：prepared 直接激活率不低于 90%；ACT→RL 每次
   `latency_ms < 1000`，目标仍是 p50 < 200 ms、p95 < 300 ms；任一 RL
   waypoint 连续 2 秒距离无至少 0.01 m 的下降时，立即输出明确 stall
   诊断。第一轮只增加证据、不改变真机运动语义，仍由现有 tracking timeout
   负责有界终止；取得动作与距离证据后再决定是否需要更早 fail-closed。

**当前状态**

已在 `zs/act-v2` 实现“两次冻结”而不是放宽阈值：ACT 余 20 steps 时完成
第一次 Plan 热身，余 5 steps 时通过同一个常驻 ROS 进程刷新 live inputs 和
trajectory；激活信号与刷新信号同时到达时，刷新具有更高优先级，避免误用旧
trajectory。日志新增每次 `planning_ms`、激活时 `frozen_input_age_ms` 和

Orin RL Follow 也已增加低频结构化 `RL Follow no progress` 警告：同一
waypoint 在 2 秒内没有至少 0.01 m 的距离下降时，记录原始归一化动作、slew

上述实现的软件回归已通过，现场效果仍为 `Needs runtime verification`。

**第二个已确认的延迟源：OctoMap QoS 不匹配**

  `Publishing latched`，即 `/occupied_cells_vis_array` 是可向迟到订阅者重放

- 本次没有 `activate_act`、ACT segment generation，也没有任何

**结论与正确操作**

**充电期间的验证边界**

挖掘机连接充电器时，现场硬件可能断开 STM32 与挖掘机之间的
传感器/执行链路。充电时的 `sensor_valid=False`、零新状态率或
`control_enabled=False` 不得用来判定策略切换性能。充电完成后必须：

1. 拔掉充电器；
2. 复位 STM32；
3. 先运行 `python scripts/diagnose_stm32_link.py`，确认 `passed=true`；
4. 再进行分阶段或自动 Mission 真机验收。

### 6.6 2026-08-24：Orin NX 16GB 只识别约 8GB

**现象与已确认证据**

- `/proc/meminfo` 显示 `MemTotal: 7727768 kB`，`tegrastats` 显示
  `RAM .../7547MB`；这不是 16GB 设备的正常保留内存差异。
- `/etc/nv_boot_control.conf` 的 `TNSPEC=3767-303-0000-...`，其中
  P3767-0000 是 Orin NX 16GB SKU；运行期模型同样声明
  `p3767-0000`。
- 当前 `/proc/device-tree/memory@60000000/reg` 声明的物理内存大小是
  `0x400000000`，即 16GiB；`/proc/cmdline` 中不存在 `mem=8G`
  之类的 Linux 限制参数。
- 内核日志却只收到 `8050304K` 总内存，说明 16GiB 的 DT
  声明并没有变成可供 Linux 使用的完整内存映射。
- `/sys/devices/system/cpu/{possible,present,online}` 都显示 `0-7`，
  `lscpu` 也确认 8 核；因此 CPU SKU 识别正常，问题集中在
  DRAM/固件内存映射，不应误判为整个模组被当成 8GB SKU。
- 手工把 `extlinux.conf` 改为 p3767-0000 的 16GB DTB 并重启后
  问题仍在，因此不是 Linux DTB 选择或内核参数问题。

**结论**

当前 QSPI 内的 MB1/MB2/UEFI/BCT 启动固件很可能含有错误的
DRAM 初始化/内存布局。DRAM 初始化发生在 Linux 之前，
所以不得用 `mem=16G` 或继续修改 `extlinux.conf` 强行解决。

### 6.8 2026-08-24：双相机改造后标准 ACT Shadow 启动失败

**故障一：主机相机路径与容器相机路径被错误比较**

- 现象：`run_act_shadow.sh` 进入容器后立即报
  `ACT and operator observation cameras must match`。
- 根因：采集配置用稳定的主机路径 `/dev/v4l/by-path/...`，ACT 配置用
  容器内路径 `/dev/video0`。二者指向同一前视相机，但属于不同设备

- 修复：标准 Shadow/Motion 启动器均从 `collection.orin.json` 读取
  `camera_front.device`，解析真实字符设备后显式映射为容器
  `/dev/video0`；Runtime 继续严格校验串口和相机分辨率/FPS，但不比较
  跨 namespace 的设备字符串。

**故障二：LeRobot 模型加载依赖隐含 import 顺序**

- 现象：越过相机检查后，模型加载报
  `AttributeError: module 'packaging' has no attribute 'version'`。
- 根因：LeRobot 通过 `packaging.version` 包属性访问版本 API，而当前
  `packaging` 不会自动加载该子模块；Dig Policy 惰性加载后，过去由
  其他模块偶然完成的隐式导入不再存在。
- 修复：只在 commissioned LeRobot ACT backend 的加载边界显式导入
  `packaging.version`，保持不使用 LeRobot 的策略 seam 仍可惰性加载。
