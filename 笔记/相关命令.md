## 0. 先看这里：应该启动哪一套

| 目标 | PC 入口 | Orin 入口 | 是否可能运动 |
|---|---|---|---|
| 不接真机学习界面 | `operator.launch.py profile:=fixture_shadow` | 不启动 | 否 |
| 看真机状态、雷达和 RViz | `operator.launch.py profile:=live_shadow` | 启动无控制授权的状态 Runtime，或复用正在运行的 Collector 状态流 | 不发送非零动作 |
| 单独验证 RL | `operator.launch.py profile:=live_commissioning ...` | 手工启动 `orin_state_sender.py` Remote RL Runtime | 是 |
| ACT 示教采集 | `run_collection_ui.py` 或 `collect_guided_episode.py` | 不手工启动；PC 脚本通过 SSH 管理 Collector | 是，按住 deadman 时 |
| 单独验证 ACT | PC 只做前置诊断 | `run_act_shadow.sh` 或 `run_act_motion.sh` | Shadow 否；Motion 是 |
| RL + ACT 混合任务 | `run_collection_ui.py` | **不要手工启动任何 Runtime** | 是 |
| 数据整理和 ACT 训练 | `excavator-il` CLI / 训练脚本 | 仅同步原始数据或部署模型 | 否 |

最重要的资源互斥关系：

```text
/dev/ttyTHS1（STM32 串口）只能三选一：
RL orin_state_sender.py  /  Collector  /  ACT Runtime

/dev/video0（前视相机）只能二选一：
Collector  /  ACT Runtime
```

不要同时启动两套 Owner。出现未知串口占用时先查明 PID 和完整命令，不使用全局 `pkill`、`killall` 或模糊清理脚本。

真机动作的共用语义顺序固定为：

```text
[boom, stick, bucket, swing]
```

- RL 输出/传输的是物理速度：`boom/stick/bucket` 为 `m/s`，`swing` 为 `rad/s`。
- ACT 和人工示教输出的是死区后归一化杆量 `[-1, 1]`，不是测得速度、PID、阀角或 PWM。
- ACT 杆量在 PC/Orin 不取反、不缩放，由 STM32 `MANUAL_ACTION` 解释。

`stick` 和状态中的 `arm` 是同一个物理自由度。RL 线上兼容字段虽然仍叫
`normalized_velocity_command`，PC 发给 Orin 的值实际已经是物理速度，不能再次归一化。

## 2. 当前网络、端口和数据方向

当前活动控制网以 `excavator-il/config/*.json` 为准：

```text
PC 有线地址：   192.168.50.1/24
Orin 有线地址： 192.168.50.2/24
```

部分旧 README 中的 `192.168.0.220/192.168.0.55` 是历史现场示例，不能直接复制到当前活动命令。

| 资源 | 方向 | 用途 | 谁监听/占用 |
|---|---|---|---|
| `18081/udp` | Orin → PC | `machine_state_v1` | PC state bridge |
| `18082/udp` | Orin 本机回环 | RL 物理速度动作 | RL Action Relay；Remote 模式强制仅 `127.0.0.1` |
| `18083/tcp` | PC → Orin | RL Follow、Mission 和固定动作 RPC | RL Runtime |
| `18090/udp` | PC → Orin | 双手柄示教命令和 ACK | Collector |
| `18092/tcp` | Orin → PC | Collector 相机预览和只读遥测 | Collector |
| `127.0.0.1:8088/tcp` | PC 本机 | 采集/混合任务 Web UI | PC UI |
| `6700/7789/6688 udp` | 雷达 → PC | MSOP / DIFOP / IMU | RoboSense 驱动 |
| `/dev/ttyTHS1` | Orin 本机 | STM32，460800 baud | RL / Collector / ACT 三选一 |
| `/dev/v4l/by-path/...` | Orin 本机 | 640×480@30 前视/倾倒双相机 | Collector；ACT 当前只使用前视相机 |

数据流总览：

```text
RL：
PC 雷达/地图/目标/规划 ──低频轨迹──> Orin RL ONNX ──物理速度──> STM32
STM32 ──状态──> Orin ──18081/udp──> PC 状态桥/TF/RViz

ACT 示教：
PC 双手柄 ──18090/udp──> Orin Collector ──杆量──> STM32
相机 + STM32 状态 + 专家动作 ──> Orin 原始 Episode

ACT 推理：
Orin 相机 + STM32 状态 ──> ACT ──杆量──> STM32
运行期不依赖 PC 手柄、deadman、UDP 或网络授权
```

首次配置或更换网卡时，不要照抄接口名。完整 `nmcli`、路由、SSH host key、NTP 和回滚步骤见：

```text
excavator-il/docs/pc_orin_direct_control_network.md
```

## 3. 每次实验前的只读检查

### 3.1 PC 检查控制网和配置一致性

```bash
ping -c 5 192.168.50.2
ip route get 192.168.50.2
ssh -o BatchMode=yes -o ConnectTimeout=5 \
  jetson16@192.168.50.2 'hostname; date --iso-8601=seconds'

cd /home/zhaoshuai/workspace_uinty/RL_prj/excavator-il
conda activate excavator-il
python scripts/check_site_config.py
```

`check_site_config.py` 只读取并交叉核对 PC/Orin IP、端口和串口引用，不修改网络。输出失败时先修改配置，不要靠临时命令覆盖。

RL 规划使用两端 UTC 时间戳。每次实验前检查 PC 的 Chrony 和 Orin 的
systemd-timesyncd：

```bash
# PC
systemctl is-active chrony
chronyc tracking

# Orin
ssh jetson16@192.168.50.2 \
  'timedatectl show -p NTPSynchronized --value; timedatectl timesync-status'
```

继续规划的基本条件：

- PC `chrony` 为 `active`；
- Orin `NTPSynchronized=yes`；
- Orin `Server` 是 PC 有线地址 `192.168.50.1`，`Poll interval` 约 16 s；
- offset/delay 在毫秒量级且持续有包计数。

仅看两端 `System clock synchronized: yes` 不能证明两台机器彼此同步。首次配置、有线 NTP
架构和验证方法见 `excavator-il/docs/pc_orin_direct_control_network.md`，不要在实验前手工
`date -s` 引入时间跳变。

### 3.2 Orin 检查设备 Owner

```bash
fuser -v /dev/ttyTHS1 /dev/video0 || true
pgrep -af 'orin_state_sender.py|excavator-il (collect|act-runtime)' || true
```

- 无输出：资源空闲；
- 已知且正是本轮要复用的 Runtime：不要重复启动；
- 未知进程：停止实验，确认其用途和退出方式；
- Web UI/引导脚本只会精确回收与当前配置匹配的已知残留进程，未知 Owner 会被拒绝。

ACT 自动混合任务还要求 Orin 用户能非交互访问 Docker：

```bash
docker info >/dev/null && echo docker-ready
```

若实验 Orin 尚未配置，可一次性执行下列命令，随后必须完全退出 SSH 并重新登录：

```bash
sudo usermod -aG docker jetson16
```

`docker` 组具备主机高权限，只用于受控实验 Orin。

### 3.3 STM32 只读链路诊断

发动机关闭，双杆回中，deadman 释放。PC 脚本通过 SSH 在 Orin 上运行只读 USART2 诊断；真正读取串口的是 Orin：

```bash
cd /home/zhaoshuai/workspace_uinty/RL_prj/excavator-il
conda activate excavator-il
python scripts/diagnose_stm32_link.py
```

继续实验的基本条件：

- `passed=true`；
- `parse_failure_count=0`；
- `control_sequence_gap_count=0`；
- 遥测和控制频率均在约 18～22 Hz；
- `max_receive_period_ms <= 80`。

该诊断不启动 Collector、不发送零命令、不写 STM32。

## 4. PC 统一 Operator：三个 Profile

统一入口为 `operator.launch.py`。正常运行时不要再分别启动状态桥、感知栈、FK、规划器或第二个 RViz。

### 4.1 `fixture_shadow`：离线学习和界面检查

```bash
cd /home/zhaoshuai/workspace_uinty/RL_prj/AiryLidar
source /opt/ros/jazzy/setup.zsh
source ros2_ws/install/setup.zsh

ros2 launch airy_excavator_bringup operator.launch.py \
  profile:=fixture_shadow
```

它在 `/offline` 命名空间启动 fixture planner、URDF/TF、Shadow Mission、RViz 和 JointState 测试滑块；不连接真机、不启动雷达、不构造动作 Backend。

### 4.2 `live_shadow`：连接真机但只观测

```bash
ros2 launch airy_excavator_bringup operator.launch.py \
  profile:=live_shadow
```

它启动 PC 状态桥、真机 FK/TF、雷达/LocalMap/OctoMap、Shadow Mission 和 RViz，但：

- 不启动 live planner；
- 不启动 Orin Edge Gateway；
- PC 不加载 ONNX；
- PC 不生成或发送真机动作。

它仍需要某个 Orin 进程把 Machine State 发到 PC `18081/udp`。若只做状态观测，可在 Orin 启动无控制授权的状态 Runtime：

```bash
cd /home/jetson16/workspace_excavator/excavator-orin-runtime
conda activate excavator-orin

python -u orin_state_sender.py \
  --serial-port /dev/ttyTHS1 \
  --control-enabled false \
  --pc-host 192.168.50.1 \
  --print-every 100
```

它占用 STM32 串口，因此不能与 Collector 或 ACT Runtime 同时运行。这里没有 Motion 授权，不会转发非零策略动作。

### 4.3 `live_commissioning`：真机规划与控制

> **运动入口。** 启动前确认作业区无人、急停可用、机构状态有效，并按第 5 节先启动 Orin RL Runtime。

```bash
ros2 launch airy_excavator_bringup operator.launch.py \
  profile:=live_commissioning \
  motion_authorization:=ALLOW_LIVE_MACHINE_MOTION \
  orin_host:=192.168.50.2 \
  orin_port:=18083
```

它在 `live_shadow` 基础上增加：

- live Plan Action Server；
- Orin Edge Follow Gateway；
- 真机 `excavation_cycle_server`；
- 分段 Action、Full Mission 和多点 Mission 的 PC 编排。

没有图形界面或只排查 launch 时可加：

```text
start_rviz:=false
```

Shadow profile 的 `motion_authorization` 必须保持默认 `LOCKED`；旧的 `live_control`、`live_motion`、`live_production` profile 已不支持。

## 5. 独立 RL 真机流程

当前 RL 和 ACT 都在 Orin 推理。RL 的正常活动拓扑是 PC 低频规划，Orin 高频执行 Follow。

### 5.1 Orin Remote 配置首次准备

Orin 的活动配置应为：

```text
/home/jetson16/workspace_excavator/excavator-orin-runtime/deploy/edge_runtime.remote.json
```

若部署机上尚不存在，先从示例创建一次：

```bash
cd /home/jetson16/workspace_excavator/excavator-orin-runtime
test -f deploy/edge_runtime.remote.json || \
  cp deploy/edge_runtime.remote.example.json deploy/edge_runtime.remote.json
python -m json.tool deploy/edge_runtime.remote.json >/dev/null
```

然后人工确认其中：

```json
{
  "mode": "remote_control",
  "remote_behavior": {
    "bind_port": 18083,
    "allowed_client_host": "192.168.50.1"
  }
}
```

还要确认 `machine_profile_path`、`urdf_path`、`onnx_path`、`mission_path` 和
`fixed_action_profile_path` 指向 Orin `deploy/assets/` 中的已校验资产。

当前 PC 检出中只有 `deploy/edge_runtime.remote.example.json`，没有现场
`edge_runtime.remote.json`，这是正常的部署边界；不要误把示例中的历史 `192.168.0.220` 当成当前 allowlist。

### 5.2 Orin 启动 RL Runtime

> **运动入口。** `--control-enabled` 和精确授权字符串必须同时存在。

```bash
cd /home/jetson16/workspace_excavator/excavator-orin-runtime
conda activate excavator-orin

mkdir -p deploy/logs
RUN_TAG=$(date +%Y%m%d_%H%M%S)

python -u orin_state_sender.py \
  --serial-port /dev/ttyTHS1 \
  --control-enabled \
  --pc-host 192.168.50.1 \
  --edge-config deploy/edge_runtime.remote.json \
  --edge-motion-authorization ALLOW_EDGE_MACHINE_MOTION \
  --print-every 100 \
  2>&1 | tee "deploy/logs/rl_follow_${RUN_TAG}_stdout.log"
```

成功标志至少包括：

```text
REMOTE EDGE CONTROL ARMED IDLE
behavior RPC ...:18083 from 192.168.50.1
sent seq=... sensor_valid=True
```

启动后处于 Idle，不会因为进程启动就自动执行 Follow。Remote 模式把动作端口强制限制在 Orin
`127.0.0.1:18082`，PC 不能向它竞争发送动作。

### 5.4 执行方式

Panel 分段验证：

1. `Plan + Follow DIG`：PC 规划到挖点，Orin RL 跟踪；
2. `ExecuteDig`：Orin 固定挖掘动作，不属于 RL；
3. `Plan + Follow DUMP`：PC 规划到倾倒点，Orin RL 跟踪；
4. `ExecuteDump`：Orin 固定倾倒动作，不属于 RL。

只验证 RL Follow 时只执行第 1 或第 3 项。一次只提交一个行为。

命令行单阶段诊断：

```bash
ros2 run airy_mission_runtime run_plan_follow_live dig \
  --mission /home/zhaoshuai/workspace_uinty/RL_prj/AiryLidar/mission/config/excavation_cycle.json
```

多挖点完整演示是运动命令：

```bash
ros2 run airy_mission_runtime run_excavation_demo \
  --program /home/zhaoshuai/workspace_uinty/RL_prj/AiryLidar/mission/config/excavation_demo.json \
  --repeat 1
```

`--repeat 2` 表示把完整点位列表重复两轮。任一步失败都会停止，不会跳过失败点继续。

### 5.5 修改 DIG/DUMP 现场点位

当前活动 Remote 流程只需要维护两份 PC 配置：

## 9. RL + ACT 混合 Mission

推荐且唯一的日常入口仍是 PC Web UI：

```bash
cd /home/zhaoshuai/workspace_uinty/RL_prj/excavator-il
conda activate excavator-il
python scripts/check_site_config.py
python scripts/run_collection_ui.py
```

Orin **不要手工启动** RL Runtime、Collector 或 ACT Runtime。UI 会管理唯一硬件 Owner，当前流程是：

```text
RL Plan/Follow DIG，同时预热 ACT 模型和 CUDA（ACT 不打开硬件）
→ RL 终态归零并退出，确认串口释放
→ UI 内部交接门放行，ACT 接管串口和相机并挖掘
→ ACT 执行时预热下一段 RL 资产和 ONNX（RL 不打开硬件）
→ ACT 终态归零并退出，确认串口释放
→ 预热 RL 接管，Follow DUMP → ExecuteDump
→ RL 保持零动作热待命，再 Follow DIG 返回对应挖点
→ 退出或开始下一铲
```

页面有两种方式：

- `开始分段验证`：每段结束后等待操作者点击下一段；点击执行 ACT 段本身就是本地显式运动授权，页面自动提供内部固定值；
- `自动装车 1～9 铲`：点击一次后连续执行，DIG 点按配置顺序循环。

旧手册中“手工输入 `ALLOW_HYBRID_MACHINE_MOTION`”已经过时，当前 UI 不要求操作者输入该口令。

默认 ACT 挖掘时间上限来自：

```text
excavator-il/config/hybrid_mission.pc.json
act.max_steps = 130
```

130 个有效 10 Hz live step 约 13 秒，是有界实验时长，不代表视觉成功检测。

Operator 可以由页面的“启动 RL + RViz”预先启动；若未启动，开始混合任务时后端会自动启动并等待就绪。若外部终端已经运行 Operator，页面会复用，不要重复启动。

停止：点击页面“安全停止”。它只中断当前精确 Owner、等待终态零并检查串口释放；它不是硬件急停。

## 13. 正常停止与资源确认

优先停止方式：

- 手工终端 Runtime：`Ctrl+C`；
- Web UI 管理的任务：页面“安全停止”；
- ROS Operator：其 launch 终端 `Ctrl+C`；
- 现场危险：硬件急停，不能用软件 Cancel 代替。

全部停止后在 Orin 确认：

```bash
fuser -v /dev/ttyTHS1 /dev/video0 || true
pgrep -af 'orin_state_sender.py|excavator-il (collect|act-runtime)' || true
```

不要再使用旧笔记里直接调用 `_rl.preflight()`、`_reclaim_stale_act_prewarm()` 等私有 Python 方法的清理命令；私有实现可能变化，而且会绕过 UI 对当前任务 Owner 的精确管理。
