## 1. 先记住当前系统结构

当前真机闭环是：

```text
PC WebUI：启动 / 取消 / 显示 / 实验证据
                         │
                         ▼
Orin Resident Mission Scheduler：按 Mission Definition 调度 Behavior
                         │
          ┌─────────────────┬─────────────────┐
          ▼                 ▼                 ▼
       RL Follow          ACT 技能          Fixed Script
       速度命令            杆量               固定动作
          └─────────────────┴─────────────────┘
                         ▼
              Resident Motion Core
       authority / generation / freshness / safety
                         ▼
              唯一 STM32 Command Sink
```

关键事实：

- 权威动作顺序始终是 `[boom, stick, bucket, swing]`。
- RL 输出物理速度：三个油缸为 `m/s`，回转为 `rad/s`。
- ACT 输出归一化杆量 `[-1, 1]`，不是速度。
- RL、ACT、Fixed 可以组合，但只有 Resident Motion Core 能把当前有效来源送给 STM32。
- `/dev/ttyTHS1` 只能有一个 owner；不能同时手工启动 RL Runtime、Collector 和 ACT Motion Runtime。
- 任何动作无效、过期、乱序，或 `sensor_valid=false`，都应拒绝非零动作并归零。

## 5. 声明式 Mission 如何组合技能

Mission Definition 是“任务配方”，Scheduler 是“执行这份配方的状态机”。当前配方位于：

```text
excavator-orin-runtime/deploy/missions/
```

当前可用 Behavior：

| Behavior ID | 技能 | 输出语义 |
|---|---|---|
| `onnx_rl_tracking` | RL 跟踪 | 物理速度 |
| `cartesian_p_tracking` | 经典 Cartesian-P 跟踪 | 物理速度 |
| `act_dig_lift` | ACT 挖掘与提升 | 归一化杆量 |
| `act_dig_transport_dump` | ACT 挖掘、运转、倾倒 | 归一化杆量 |
| `fixed_dig` | 固定挖掘动作 | 归一化杆量 |
| `fixed_dump` | 固定倾倒动作 | 归一化杆量 |

不同实验应通过 Mission Definition 组合 Behavior，不应复制一套新的串口、安全门或状态机。

## 6. 配置修改手册

这一章是自己调整项目参数时的权威入口。修改前先区分三类文件：

| 类型 | 含义 | 能否直接改 |
|---|---|---|
| 源配置 | 人编辑的权威参数 | 可以，但要校验和留 diff |
| 部署快照 | 由源配置生成，含 SHA-256 和 Mission 身份 | 不直接改，用脚本重建 |
| 运行产物 | log、data、model、export | 不当配置改，不进 Git |

当前为什么 PC 和 Orin 都有“看似相同”的文件：

```text
PC 源配置
  → 校验、建立 Mission/target 快照、计算 hash
  → Orin 部署快照（执行权威）
  → PC 启动配置保留 expected ID/hash（反向对账）
```

这不是要人工同时改两份坐标。正确方式是：只改源配置，然后用受控脚本生成、同步和对账。

### 6.1 通用修改流程

```text
1. 安全停止 Mission，确认串口/相机无 owner
2. 记录修改前 Git HEAD 和配置值
3. 只改一类参数
4. 运行 JSON/schema/定向测试
5. 重建并同步部署快照
6. 重启 UI/Runtime
7. 发动机关闭检查启停和归零
8. 真机按 1 铲 → 小多铲扩大，不一次同时改多个参数
```

查看当前改动：

```bash

  mission/config localmap/config
git -C /home/zhaoshuai/workspace_uinty/RL_prj/excavator-il diff -- config
git -C /home/zhaoshuai/workspace_uinty/RL_prj/excavator-orin-runtime diff -- deploy
```

### 6.2 修改挖掘点坐标、数量和循环顺序（常用）

唯一源文件：

```text
AiryLidar/mission/config/excavation_dig_point_catalog.v1.json
```

当前实际是 5 个点，不是旧三点也不是代码写死的八点。点数可以改为任意非空数量。

```json
{
  "schema_version": "excavation_dig_point_catalog.v1",
  "frame_id": "machine_root_ros",
  "dig_points": {
    "dig_near_01": [1.10, 0.55, 0.00],
    "dig_near_02": [1.10, 0.25, 0.00]
  },
  "default_dig_group": "all",
  "dig_groups": {
    "all": ["dig_near_01", "dig_near_02"]
  }
}
```

规则：

- 坐标单位为米，坐标系必须是 `machine_root_ros`。
- `dig_points` 中每个 key 唯一。
- `dig_groups` 只能引用已存在的 key，组内不重复。
- 点集中的顺序就是自动多铲的循环顺序。
- `default_dig_group` 必须存在且非空。

修改后在 PC 执行：

```bash

  mission/config/excavation_dig_point_catalog.v1.json >/dev/null

cd /home/zhaoshuai/workspace_uinty/RL_prj/excavator-il

python scripts/sync_v3b_dig_catalog.py --dry-run
python scripts/sync_v3b_dig_catalog.py --check-idle
python scripts/sync_v3b_dig_catalog.py
```

同步脚本会：

1. 严格校验 catalog；
2. 为主线、经典跟踪、固定挖掘和工程参考四个 Mission 重建 candidate；
3. 备份 PC 和 Orin 上一版 candidate；
4. 同步到 Orin；
5. 重新校验坐标、顺序、Mission ID 和 SHA-256。

然后重启 UI。坐标变更后先启动 RViz 核对 marker，发动机关闭逐点试跑，再做真机运动。

不要直接改：

```text

excavator-orin-runtime/deploy/v3b/**/candidate/target_catalog.candidate.json
```

这些都是可再生的部署快照，下次同步会覆盖手改内容。

### 6.3 修改倾倒点和终点到达容差（常用）

源文件：

```text
AiryLidar/mission/config/excavation_cycle.json
```

当前关键值：

```json
{
  "targets": {
    "dump": {
      "position_m": [-0.20, -0.90, 0.10],
      "radius_m": 0.25
    }
  },
  "limits": {
    "waypoint_tolerance_m": 0.25,
    "waypoint_dwell_s": 0.0,
    "tracking_timeout_s": 60.0,
    "settle_s": 0.5
  }
}
```

各字段的真实含义：

| 字段 | 当前值 | 对当前 Resident Mission 的影响 |
|---|---:|---|
| `targets.dump.position_m` | `[-0.20,-0.90,0.10]` | RL 运料的倾倒终点 |
| `limits.waypoint_tolerance_m` | `0.25 m` | 动态轨迹的起点和最终 DIG/DUMP 点到达球半径 |
| `limits.tracking_timeout_s` | `60 s` | 单段 Follow 超时上限 |
| `limits.waypoint_dwell_s` | `0` | 当前 Orin Follow 要求为 `0`，不要设为非零 |
| `targets.*.radius_m` | `0.25 m` | Airy Mission/Panel 的目标契约半径，不是 Resident Follow 的唯一到达阈值 |

“可达大小”通常指 `waypoint_tolerance_m`。数值越大，越早判定到达，但终点精度越低；
数值越小，定位更严，但更可能在死区、液压延迟和传感器噪声下久等或超时。


### 6.5 别把四种“半径”当成同一个参数

| 概念 | 配置 | 作用范围 |
|---|---|---|
| 终点到达容差 | `excavation_cycle.json -> limits.waypoint_tolerance_m` | 当前 Resident Follow |
| 中间点到达容差 | sync 脚本的 `--intermediate-waypoint-tolerance-m` | 只影响圆弧中点 |
| RRT* 目标掩膜 | `localmap/config/planning.json -> planner.goal_mask_radius_m` | PC RRT* 碰撞地图处理 |
| 可达工作空间 | `localmap/config/reachable_workspace...json` | PC planner 的几何可达体积 |

当前 `fixed_target_hybrid` 的 Resident Follow 是 Orin 本地动态三点圆弧，**不使用 PC RRT***。
因此修改 `planning.json` 中的 `step_size_m`、`goal_mask_radius_m` 或 `max_iterations`，不会改变
当前主线自动铲装的三点轨迹。

另外，`planning.json` 当前为：

```text
planner.execution_workspace_mode = disabled_by_operator
```

所以可达工作空间尚未成为当前真机主线的强制运动门。不要修改可达域文件后就假设真机已受该体积限制。

### 6.6 修改 ACT 执行步数（谨慎）

ACT 步数是 Mission Behavior 的有界预算，当前仅挖掘为 `130 steps @ 10 Hz`。

主线需同时对账：

```text
excavator-orin-runtime/deploy/missions/fixed_target_hybrid.json
  cycle_behaviors[].max_steps

excavator-il/config/resident_fixed_cycle.pc.json
  act_max_steps
```

其他任务有各自的 Mission Definition 和 PC runtime config。工程参考策略当前为 `260 steps`。

修改 Mission Definition 会改变 `mission_sha256`。重建 candidate 后还必须更新对应：

```text

hybrid_evidence*.pc.json                     -> mission_sha256
config/experiments/icra2027/<profile>.json   -> expected_mission_sha256
```

因此这不是“只改一个数就真机跑”的参数。修改后必须让严格 profile 检查全部通过：

```json
  "action_valid_for_ms": 300,
  "follow_action_startup_slew_rate_per_s": 6.0,
  "follow_action_slew_rate_per_s": 3.0
}
```

含义：

- `startup_slew_rate_per_s`：策略交接后起步阶段的变化速率上限；
- `follow_action_slew_rate_per_s`：正常 Follow 阶段的变化速率上限；
- 数值越大越接近策略原始输出，但液压冲击和抖动风险也越高。

ACT/人工杆量的尾段死区契约是独立文件：

```text
excavator-orin-runtime/deploy/manual_action_deadzone.f407.json
```

它当前按 F407 `MANUAL_ACTION_DEAD_ZONE` 为四轴正反向 `0.15`。这与 RL 物理速度死区不是同一契约。

`shared/machine_profile.json -> deploy.software_deadzone` 是历史兼容值，注释已明确说当前 policy
path 会绕过它。不要用这个统一 `0.15` 去替代每轴 RL 死区，也不要把它当成 ACT 杆量校准。

修改速度/死区/斜率后必须先运行 host 回归，再做发动机关闭试验，最后从 1 铲开始。

### 6.11 更换 ACT 模型（高风险）

不要只替换 `model.safetensors`。一套部署至少需同时保持：

```text

```
