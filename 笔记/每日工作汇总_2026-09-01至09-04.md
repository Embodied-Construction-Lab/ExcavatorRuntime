## 这四天为什么集中做这些工作

前一阶段已经证明挖掘机可以完成多铲任务，但“能够演示”还不能直接回答论文问题。原有系统把任务顺序、

## 9 月 1 日（周二）：声明式 Mission 落地与真机安全链排障

### 为什么这样做

- 论文需要比较 RL 与经典控制、ACT 与固定挖掘。如果为每个实验复制一套状态机，除了被替换算法之外，
  时序、容差和安全逻辑也可能一起变化，实验就失去“单一变量对照”的意义。
- PC、Orin、ACT worker 和目标 catalog 分处不同进程与设备。仅靠文件名或 UI 标签不能证明实际运行了
  哪个模型和任务，因此必须在运动前核对 Mission ID、定义 SHA、Behavior 和模型 SHA。
- `MOTION_GATE_CLOSED` 与 `ACT_AUTHORITY_LOST` 是安全链的主动结果。先把撤权原因查清，才能避免为
  追求成功率而误删正确的 fail-closed 行为，也能把硬件故障与策略效果分开统计。

### 完成工作

- 将原来写在状态机分支中的任务组合重构为声明式 `Mission Definition`：
  - `fixed_target_hybrid`：RL 到挖掘点 → ACT 挖掘提升 → RL 运料 → 固定倾倒 → RL 返回；
  - `classical_tracking_hybrid`：只把 RL Follow 替换为 Cartesian-P；
  - `fixed_dig_hybrid`：只把 ACT 挖掘替换为固定动作；

- Mission Definition 与 Scheduler、Behavior Adapter、Resident Motion Core 分离；所有策略仍通过唯一
  STM32 Owner、authority、generation、freshness、terminal-zero ACK 和安全门执行。
- PC Runtime 升级为严格 v6 身份契约；Owner READY 返回 Mission ID/SHA、ACT Behavior 和模型 SHA，
  PC 在运动前逐项核对。

## 9 月 2 日（周三）：IMU 基线回退、回转安全与 UI 遥测解耦

### 为什么这样做

- yaw 不只是 UI 上的显示值，也是 RL 判断回转方向、距离与终点的重要观测。若符号、比例、环绕或新鲜度
  错误，策略即使输出正确，也会因为错误反馈持续向同一方向回转。
- 在重要演示前先回到已验证固件基线，是为了一次只验证一个变量：先确认主线能恢复，再单独评估零偏补偿，
  避免同时修改估计、限位和控制后无法定位回归来源。
- UI 遥测是观察通道，不应成为 ACT worker 或相机预览的附属生命周期。将其解耦后，显示中断不会改变
  运动控制；反过来，UI 上的旧值也不应再被当作判断 Orin 实时观测是否正常的依据。
- 起点/终点与中间点使用两级容差，是在“到点精度”和“液压死区附近长时间停滞”之间做明确取舍，而不是
  随现场观感不断修改同一个隐含常数。

### 完成工作

- 针对真机约转到 `180°`、运行时状态/RViz 一度不足 `90°`，以及 UI 显示 `338.9°` 的问题，梳理
  yaw 的范围、单位、正方向、环绕和“本次上电相对角”语义。
- 确认新增启动零偏补偿本身不可能在数秒内制造上百度误差，但时间戳异常后的积分恢复、运行中状态
  新鲜度和不同显示链路仍存在风险。为重要演示建立并使用 F407 `zs/imu-baseline-ab` 基线。
- 在该基线加入相对本次上电方向的 `±180°` 回转限位，并通过 host 测试；提交为 `c7f1ecc`。
- 把 UI 机构状态从 ACT/相机预览生命周期中拆出，建立独立 machine-state telemetry bridge。相机预览
  仍走 HTTP，但 UI 状态显示不再依赖 ACT worker；只读 UI 链异常不应影响 RL/ACT 运动闭环。
- 解释相机不并入普通状态报文的原因：图像带宽和频率远高于结构化遥测，应走独立视频/预览通道，
  而关节、油缸、yaw 和安全状态走轻量状态通道。
- 对 waypoint 容差进行现场试调，最终把活动终点到达容差恢复为 `0.25 m`，圆弧中点容差保持
  `0.40 m`；新增独立教程说明起点/终点共用容差与中间点容差分别在哪里修改。
